# UFS v174 软件与交付证据

## 边界和恢复基线

本轮没有连接板子、SSH或写物理设备。v174为大块存取候选，实机速度/冷读/重启持久性/
长稳仍待用户测试。v173小文件实机持久性与大cp中断的区别记录在
[追加证据](UFS_V173_RUNTIME_20261022.md)，没有追改旧封存manifest。

旧SD镜像v173保持SHA256 `7e606b28ee9f169992447a3c50f6b904667a52436846a54c39d60d77c6648fbf`。
开发前完整恢复点945文件/3引用，包含原dirty bytes/index/history，不只记录HEAD。
所有历史文档、镜像、源归档和恢复点保留。原Linux项目不改。

- 驱动整合38场景：新增RO分区无write/ioctl、无需scratch、重复/身份拒绝、RO/RW互斥；

  quiesce454读故障+6写故障、handoff80、board65、link3357+577继续回归。
- NSH大偏移补丁与官方FAT32稀疏普通文件元数据检查继续回归。
- SDK清理正常/拷贝失败/信号3场景新增第四应用目录恢复；项目恢复工具3场景保留。

相应日志 `out/v174-*.log`。主机不会挂载/格式化真实UFS。

## 编译、暂存与镜像门禁

12个真实ARM64驱动/板级对象＋新应用ARM64对象通过；应用最大单帧1536B，任务栈8192B。
单帧不是整条调用链峰值，后续上板仍应检查stack余量。51关键overlay源和5应用源
分别在暂存早晚核对；NSH patched源额外核对。旧51关键源48个不变，仅UFS主驱动/data
头和data源增加RO路径；原writer从gate开始逐字不变，不移除回读/flush。

最终完整构建、ELF/Image布局、SDK恢复、镜像内核提取、非SD分区3逐字不变及源码归档
由 `out/package-v174.sh` 和 `out/deliver-v174.py` 执行门禁。实际完成值和SHA256见
[ARTIFACTS](../ARTIFACTS.md) 与 `out/v174-final-integrity.json`；最终文件缺失或非成功
时，不得将开发中日志当成最终完整交付。

最终构建2984目标已通过；ufs_main实际链接地址4028d9cc，文件2743400B、runtime37363712B。
NOP/read arena各77824B，bench65536B、scratch73936B、data144B独立BSS布局通过。
原生Windows审计171项SDK暂存路径已逐字恢复，路径名统一POSIX避免平台假差异。
在SDK恢复后重新运行NSH dd回归通过；早期v174-dd-host.log的失败发生在SDK已暂存
patched源时，测试期望原源而断言失败，保留日志但不作为最终结果，最终以dd-host-final为准。
镜像内核提取hash与本次构建完全一致，旧GPT分区4未对齐提示继承自基线，不擅改GPT。

默认不开机执行UFS/复制任务。整盘只读、固定第三分区/尾部保留、只读新别名、手动RW门禁
都保留。未验证HS Gear切换，不声明UFS3.1标称Gbps或实机持续吞吐。

## 后续验收

按 [v174测试流程](../a733/UFS_BULK_V174.md) 挂载原数据卷检查旧模型大小/compare，不重格式化；
需要时用新名字copy并核对verified/SHA256。记录copy/verify分别耗时、纯文件读速度、
驱动writes/flushes增量、模型load时长、隔离状态，再干净umount并重启复查。
源模型复制期间不要修改；不允许自动加载残片或为速度关闭未经同步契约验证的flush。

集成检查补充：首次配置尝试发现本SDK开关实际为CRYPTO_MBEDTLS，而非MBEDTLS；已中止
第一次构建并正常还原，修正后最终配置必须SYSTEM_A733STORAGE=y且ELF包含ufs_main。
另查到NSH mount只有-t/-o，无-r；FAT bind强制fat_mount(fs,true)，VFS亦检查块write。
所以新增RO块视图仅用于原始读，不提供只读FAT挂载；文档不发送不可执行的mount -r。
SDK恢复审计改用POSIX相对路径，消除Windows/WSL分隔符导致的假不匹配，仍逐字比hash。
