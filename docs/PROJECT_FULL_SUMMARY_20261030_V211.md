## 一、当前总体状态

### 1.1 已经实机成立的主要能力

目前有实机证据支持的核心能力包括：

- A733启动openvela，进入NSH。
- 8核SMP运行，识别6个Cortex-A55和2个Cortex-A76。
- 4GiB内存的分区堆和固件保留区域处理。
- SD卡、GPT分区、FAT文件系统及`/data`读写。
- FCU760K板载Wi-Fi扫描、WPA2连接、DHCP和网络通信。
- SSH、FTP、HTTPS、NTP等维护服务的基本使用。
- 官方Agent接入DeepSeek/MiMo，连续中文对话。
- 本地Qwen和MiniCPM5模型的CPU推理。
- ST7735屏幕显示、LVGL表情切换及Agent表情联动。
- ICS43434麦克风录音。
- MAX98357A扬声器播放录音文件。
- VIP2 NPU自检、LeNet、YOLOv5和YOLOv8模型执行。
- 旧关键词模型的多模型连续推理验证。
- Kingston UFS数据读写、模型复制校验和模型加载。
- UFS一次正常重启后的自动挂载。
- Radxa 13M 214摄像头RAW采集、图像处理、SPI显示。
- 摄像头→YOLO→SPI识别框展示的短时连续运行。
- BLE控制器查询、官方Host扫描及多轮启停。

### 1.2 已实现并通过软件验证，但不能算整机实机通过的能力

主要包括：

- 新版通用Zipformer ASR的openvela后端。
- 完整离线语音会话编排。
- CPU声学模型＋NPU声码器的新版流式TTS。
- v209的实际绑核确认和三阶段视觉流水线。
- v210、v211的语音延迟优化。

## 二、项目目标与最终产品形态

项目实际包含三层目标。

### 2.1 平台目标

让原本缺少完整支持的A733/Cubie A7Z能够运行openvela，并具备：

- 可启动、可调试、可恢复的系统。
- CPU、内存、中断、存储、总线和网络支持。
- NPU、音频、显示和摄像头适配。
- 可复现的构建、镜像生成和验证流程。

### 2.2 AI应用目标

在板端实现：

- 云端与本地文字对话。
- 本地语音识别。
- 本地LLM生成。
- 本地语音合成。
- 桌宠表情反馈。
- 摄像头视觉识别。
- 受限、可确认的下位机控制。

### 2.3 产品目标

最终希望形成一个：

> 能听、能说、能看、能显示表情、能离线思考，并能通过UART或BLE控制下位机的openvela端侧AI主控。

目前已经具备多数基础构件，但距离“开机后无需人工维护、所有能力统一运行的稳定产品”仍有集成和验收工作。

### 3.2 是否基于官方Agent

**云端Agent路径是基于官方Agent框架的。**

使用了官方组件中的：

- 消息总线。
- Agent上下文处理。
- LLM代理。
- TLS通信。
- Skills机制。
- 工具注册与调用机制。

项目新增的是：

- 桌宠通道桥接。
- 初始化与凭据保存。
- 云端/本地/规则路由。
- 本地LLM适配器。
- 音频、屏幕及STM32工具适配。
- 请求关联、错误处理和生命周期保护。

但是，不能把所有执行路径都描述为“完整经过官方云Agent”。

例如：

- 简单规则可以直接回复。
- 明确的STM32短指令可以绕过LLM。
- 离线语音入口强制使用本地模型，并禁止动作和云端调用。
- 本地LLM运行时是项目移植，不是官方现成的MiniCPM5后端。

### 3.3 不能混淆的几个概念

1. NSH来自NuttX，不代表项目没有使用openvela。
2. WAPI是Wi-Fi控制接口，不替代FCU760K芯片驱动。
3. 官方LVGL不意味着所有显示底层都不需要板级适配。
4. 项目PCM接口已用于应用，但不等于完整标准Media音频设备已完成。
5. 摄像头已能采集RAW，不等于完整ISP、V4L2和录像编码服务已完成。
6. NPU可以执行准备包，不等于已经实现通用ONNX/NBG编译器。

## 五、启动、CPU、内存与内核适配

### 5.1 启动链

当前复用厂商已经存在的：

```text
Boot0 → SCP/固件初始化 → U-Boot/BL31交接 → openvela → NSH
```

项目没有重新实现整个厂商引导链。

内核包含ARM64 Image头，使用U-Boot的`booti`路径进入，不能按裸程序用`go`替代。

需要区分：

- U-Boot临时加载地址。
- ARM64 Image头描述的运行地址。
- BL31最终交接地址。

因此必须使用与该版内核配套的引导脚本，不能随意混用旧脚本和新Image。

### 5.2 CPU和SMP

A733实际运行拓扑为：

- CPU0～CPU5：Cortex-A55。
- CPU6～CPU7：Cortex-A76。

已经处理和验证过：

- 主核启动。
- 次核启动。
- 每核栈与页边界。
- GIC重分发器映射。
- CPU逻辑编号与硬件亲和性对应。
- 多核任务执行。
- 亲和性检查。
- 异常输出。

历史上出现过：

- 次核零地址异常。
- 启动栈越界或边界配置问题。
- 多核启动打印交错。
- 设置affinity成功但指令尚未真正迁移。

这些问题不是同一种原因，不能统一归为“电源问题”或“串口乱码”。

### 5.3 内存

板上内存为4GiB。

实现中不是简单把全部地址无差别交给一个堆，而是：

- 保留固件区域。
- 使用分区堆暴露可用内存。
- 对DMA和NPU区域单独规划。
- 检查低地址启动区域边界。
- 对RAW缓冲和特定工作区添加保护。

关键历史约束包括：

```text
DRAM起始：0x40000000
openvela运行入口：0x40200000
BL31保留区：0x48000000..0x48ffffff
```

v211最终ELF核验：

- 24个构造器。
- runtime end：`0x45de6000`。
- 摄像头RAW固定池：`0x45913000`，4MiB。
- 仍在相应启动内存边界之内。

### 5.4 中断、定时与异常

已接入：

- GICv3。
- ARM通用定时器。
- 异常向量。
- MMU与缓存基础处理。
- 信号、任务和NSH运行基础。

异常日志能够输出：

- 当前CPU。
- CurrentEL。
- ESR。
- ELR。
- FAR。
- LR、SP。
- 通用寄存器。

实际调试时必须使用**对应版本的未剥离ELF和map文件**解析地址，不能拿其他版本ELF猜测。

### 5.5 尚未完成的系统级工作

不能把八核启动成功扩展为：

- 生产级DVFS完成。
- 完整热管理完成。
- 所有中断路由和负载都已压力验证。
- 挂起/恢复完成。
- 数小时全负载运行完成。
- 所有强制删除任务场景都可安全恢复。

## 七、SD卡、文件系统与数据组织

### 7.1 SDMMC

当前SDMMC0采用：

- 初始化低速。
- 4-bit总线。
- 已验证的PIO传输路径。
- 历史配置中传输频率为12MHz。

因此大模型冷加载速度较慢是有实际实现背景的，不是“SD卡标称速度”就能保证软件达到。

### 7.2 分区与挂载

SD镜像使用GPT，区分：

- 固件区域。
- EFI区域。
- openvela启动分区。
- data分区。

板端常用数据根目录：

```text
/data
```

已经支持FAT读写和UTF-8长文件名相关处理。

### 7.3 常用数据位置

```text
/data/aic/                       Wi-Fi/Bluetooth固件
/data/models/                    本地LLM模型及传输文件
/data/npu/                       NPU模型和输入
/data/npu/general-asr/           新通用ASR资产
/data/npu/general-tts/           新本地TTS资产
/data/ai_agent/config/           Agent、音频、路由等配置
/data/ai_agent/device.key        板上凭据加密密钥
/data/ai_agent/skills/           Agent Skills
/data/ai_agent/memory/           Agent相关记忆资料
/data/ai_agent/sessions/         Agent会话资料
```

这里要区分：

- 官方Agent的会话/记忆目录。
- 本地LLM保存在RAM里的有限对话历史。

它们不是自动同步的一套记忆系统。

### 7.4 文件系统限制

当前FAT路线存在：

- 单文件小于4GiB的限制。
- 不能把文件权限当作强物理安全边界。
- 异常断电一致性不能仅靠`rename`就作完整保证。
- 大模型复制后仍需要完整摘要校验。
- 0字节残留文件不能当作有效模型。

## 八、UFS高速存储

### 8.2 已实现的分阶段能力

UFS不是一次性开放所有操作，而是逐层推进：

1. 板级只读快照。
2. 固件交接状态采集。
3. 队列静止和所有权确认。
4. 私有DMA缓冲及NOP。
5. 真实只读命令。
6. 标准只读块设备。
7. 固定scratch窗口写入、flush、回读和还原。
8. 限定数据分区视图。
9. FAT32文件系统。
10. 大块模型复制。
11. 完整SHA256比对。
12. 读取性能测试。
13. 自动挂载。
14. Agent模型路径选择。

主要源码分布在：

- `a733_ufs.c`。
- `a733_ufs_board.*`。
- `a733_ufs_handoff.*`。
- `a733_ufs_quiesce.*`。
- `a733_ufs_nop*`。
- `a733_ufs_readcheck.*`。
- `a733_ufs_scratch.*`。
- `a733_ufs_data.*`。
- `app/a733storage`。

### 8.3 当前设备视图

- `/dev/ufs0`：整盘只读视图。
- `/dev/ufsdata`：经过限定的数据卷视图。
- `/ufs`：模型数据卷挂载点。

不能把当前实现描述为：

- 任意UFS器件通用驱动。
- 任意GPT分区管理器。
- 可随意发送任意SCSI命令的工具。
- 已完成从UFS直接启动openvela。

### 8.4 已有实测

v174记录：

- 约1.117GB Qwen模型完整复制并SHA256验证成功。
- 128MiB连续读取约1894ms。
- 对应约**67.58MiB/s**。
- Qwen模型从UFS冷加载约**15.99秒**。
- 历史SD加载同类模型约175秒。
- 重启后完整compare成功。

这是当前软件路径实测，不是UFS3.1总线极限。

### 8.5 自动挂载

自动流程运行在独立任务，不占住NSH输入。

大致顺序为：

```text
board → handoff → quiesce → dma-nop
→ readcheck → block-ro → data-existing → mount
```

主要原则：

- 一步失败就停止。
- 不自动格式化。
- 不自动清旧引导器。
- 不自动执行scratch写入。
- 不反复复位碰运气。
- 失败时保留SD和其他服务可用性。

用户后来执行持久开关后，已有一次：

```text
attempted=1
ready=1
error=0
stage=mounted-existing-FAT
```

因此可以说“正常重启自动挂载有通过记录”，不能说“所有冷启动和异常断电都已通过”。

### 8.6 当前最重要的限制

**独立PMIC/M-PHY完整冷初始化仍未完成。**

当前有效路径仍依赖引导固件留下可接受的UFS链路状态。

因此：

- 固件没有初始化好UFS时，RTOS不能保证自行从零恢复。
- `ufs start`不是万能修复命令。
- 不应为了挂载成功反复格式化或强制复位。

### 8.7 旧UFS引导器残留

这是尚未最终处理的问题。

已有证据显示：

- 正常路径进入SD中的较新引导链。
- 异常路径会进入UFS里的旧Boot0/U-Boot。
- 旧链可能出现无法识别MMC、错误容量、扫描后异常等情况。

已完成：

- 导出UFS前2MiB原始备份。
- 解析GPT和两份BOOT0。
- 定位旧引导标记。
- 准备只修改特定标记、可恢复的Linux维护工具。
- 离线验证备份、边界、短写、回读和恢复行为。

**没有证据表明已经在实盘执行禁用。**

不能说“已经删除UFS里的U-Boot”。

相关说明见[UFS旧引导链处理记录](D:/My-Program/AI-Agent-Program/GPTsprogram/Openvela/A733-A7Z-ALL-Files/contest2026_274_Dogking-dev-ai-contest-2026/docs/a733/UFS_BOOT_CLEANUP_20261023.md)。

## 十三、I2S麦克风与扬声器

### 13.1 当前硬件主线

收音：

```text
ICS43434
```

放音：

```text
MAX98357A＋扬声器
```

当前已验证的是用户提供的合并模块路线。

旧INMP441代码保留，但没有获得可信的录音内容通过结论。

### 13.2 信号接线

| 功能 | A7Z引脚 | 物理Pin | 合并模块信号 |
|---|---|---:|---|
| I2S位时钟 | PB5 | 12 | BCLK、SCK |
| I2S左右时钟 | PB6 | 35 | LRCLK、WS |
| 扬声器数据 | PB7 | 40 | 功放DIN |
| 麦克风数据 | PB8 | 38 | 麦克风SD |
| 地 | GND | 如6 | GND |

注意：

- 功放DIN和麦克风SD不能短接。
- 两组时钟不能凭外观假定模块内部已相连。
- 合并模块VCC与裸ICS43434的VDD不是一回事。
- 扬声器接差分输出两端，任何一端都不接GND。

### 13.3 时钟与格式

当前主线：

- 48kHz。
- 双slot。
- 每slot 32bit。
- BCLK约3.072MHz。
- 麦克风24bit数字PCM。
- 应用语音转换为S16。
- 默认语音增益×5。

ICS43434是数字I2S PCM麦克风，不是PDM麦克风。

### 13.4 已修复的问题

包括：

- 使用了错误引脚布局。
- FIFO状态位解释错误。
- 空FIFO被重复读取。
- 录音文件是5秒长度，但真实采样时间不足。
- RX硬件帧计数与双槽FIFO字数混淆。
- 通道映射和左右slot处理。
- S24到S16转换。
- 默认增益不足。
- 录音期间功放数据脚没有保持确定电平。

### 13.5 录音电流声修复

功放和麦克风共享BCLK/LRCLK。

只关闭TX并不保证功放DIN为低，因此录音时可能发出电流声。

v162在录音和空闲阶段将PB7切为GPIO输出低；播放时再恢复I2S输出。

这是**数据线静音**，不是伪造一个模块没有引出的硬件shutdown控制脚。

用户之后确认录音期间电流声消失。

### 13.6 已有实机通过范围

有记录支持：

- ICS43434录到真实人声。
- 默认×5增益被用户认为合适。
- 两次录音。
- 五次48kHz单声道WAV回放。
- 用户听到清楚的说话声和拍手声。
- 每次约5秒。
- 样本和硬件计数匹配。

### 13.7 音量与增益

要区分两套设置：

- 早期诊断节点的音量：主要为本次开机内设置。
- 应用音频配置：持久保存，默认音量50、增益×5。

当前应用支持：

- 音量0～100。
- 录音增益1～16。
- I2S输出或关闭输出。

音量百分比是PCM线性幅度，不是声学响度百分比。

### 13.8 当前音频架构限制

当前已有项目公共PCM接口，将寄存器操作留在vendor侧。

但仍不能宣称：

- 标准音频DMA lower-half全部完成。
- 完整Media Recorder/Player/Policy接管。
- 全双工。
- AEC回声消除。
- 打断播放即时录音。
- 任意采样率和任意音频编码均支持。

### 14.5 内存演进

早期语音检查点曾使用：

- 约2MiB Tensor I/O池。
- 24MiB prepared区域。
- 32MiB DMA arena。

新通用ASR较大，不能套用旧容量。

新实验配置独立规划为：

- 80MiB DMA arena。
- 8MiB Tensor I/O。

### 14.6 安全与故障原则

- 不接受错误CID、长度、布局和越界。
- 不跳过必要输出检查。
- 不将旧输出当新输出。
- 不自动重试不确定的硬件任务。
- 不在DMA仍可能持有内存时释放。
- 所有权不明时隔离并要求重启。

这是一套受控运行时，不是允许不可信用户任意提交NPU机器命令的安全沙箱。

## 十七、完整离线语音会话

### 17.1 当前目标链路

当前离线语音测试入口明确：

```text

```

其目的是先验证语音和聊天链路，避免：

- ASR误识别导致运动。
- LLM生成动作被直接执行。
- 不完整语音链路被当作安全控制系统。

因此：

> “离线语音聊天候选已接通软件路径”与“离线语音控制STM32已全部完成”是两个不同结论。

### 17.5 3–5秒目标

> 真实结束说话，到首段有效回复语音从扬声器发出。

必须包含：

- ASR积压与收尾。
- LLM首短语。
- CPU声学。
- vocoder。
- 播放起始缓冲。

不能用：

- 首token。
- TTS首PCM。
- 驱动首次取样。
- 预生成语音。
- 固定问候。
- 空白音频。

代替这一指标。

包括：

- CRC16-CCITT-FALSE。
- 序号匹配。
- PING/PONG。
- ACK/NAK。
- MOVE。
- SERVO。
- STOP。
- 故障和完成事件。

### 21.4 生命周期

- 单一串口任务拥有UART。
- 独立后台任务，不依附短命NSH线程。
- 周期心跳。
- 失联关闭运动权限。
- 重连不自动解锁。
- 命令ACK有期限。
- 超时不自动重发运动。

### 21.5 Agent接入

有两种入口：

1. 明确短指令走受限直接路由。
2. 官方云Agent调用`stm32_control`工具。

安全约束：

- 工具动作必须符合本轮用户原文。
- 限制参数。
- 一轮最多消费一次动作额度。
- STOP优先。
- 禁止模型自动arm。
- 禁止模型清故障或绕过热保护。
- ACK不等于物理动作完成。

### 21.6 当前不足

用户反馈过：

- 部分命令电机无动作。
- 反复需要`arm`。
- 舵机未接导致动作验证不完整。

目前不能把整个机械执行链称为完成。

另外，STOP后关闭运动权限、超时重新arm是安全策略的一部分；不能为了方便直接取消。

更合理的后续方向是：

- 清楚显示为什么未armed。
- 区分故障、掉线、超时和正常STOP。
- 在明确安全前提下设计操作会话。
- 先验证协议，再验证机械动作。

协议和边界见[STM32 UART4接入说明](D:/My-Program/AI-Agent-Program/GPTsprogram/Openvela/A733-A7Z-ALL-Files/contest2026_274_Dogking-dev-ai-contest-2026/docs/a733/AGENT_UART4_STM32_V177.md)。
